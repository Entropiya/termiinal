# Этап 1 — прототип рисков

Цель: до постройки UI убедиться, что нарезка блоков вообще может работать на Windows через ConPTY.
Если что-то из этого не работает, вся архитектура «блоков» из ТЗ требует пересмотра ещё до того,
как вложен труд в интерфейс.

## Что проверяем

- [x] **OSC-маркеры доходят целыми.** Перепроверено на реальном Debian (`192.168.70.167`) через
      `ssh.exe` после фикса сырого ESC-байта: строка внедрения видна в эхе целиком, без
      пропавших кусков.
- [x] **Текст команды совпадает с реально выполненной.** Перепроверено на реальном Debian
      с активной (исправленной) интеграцией — без задвоения символов и искажений.
- [x] **Внедряемая строка не остаётся в истории.** Перепроверено на реальном Debian с
      исправленной версией.
- [x] **Headless-рендер даёт чистый текст.** Механика `\r`-перерисовки подтверждена синтетическим
      тестом (кнопка «Тест `\r`-перерисовки») и затем вживую на реальном Debian (`apt update`
      под активной интеграцией) — без мусора от промежуточных кадров.
- [x] **Риск ConPTY с печатаемым маркером.** Не понадобился: живые OSC-маркеры (после фикса
      с `\e`) доходят корректно и на Git Bash, и на реальном ssh-таргете. Оставляем как
      задокументированный план Б на случай другого шелла/окружения, где маркеры всё же собьются.

**Этап 1 закрыт.** Все пять пунктов подтверждены на реальном Debian-таргете. Два реальных бага,
найденных и исправленных по пути — дедлок в `pty.rs` и сырой ESC-байт в инъекции — задокументированы
в разделе «Находки» ниже; ни один не был предсказан на бумаге до того, как дошло до реального теста,
что и было целью этого этапа.

## Инфраструктура этапа

- Tauri-проект с минимальным Rust-бэкендом: `portable-pty` поднимает ConPTY, запускает `ssh.exe`
  (или локальный `cmd`/WSL для первых тестов), поток байт идёт во фронтенд через Tauri event.
- Фронтенд: `xterm.js` для отображения + `@xterm/headless` для теневого рендера блока агенту.
- Тестовая цель для ssh — Debian-машина с bash (нужен отдельный тестовый хост или контейнер, не
  связанный с другими проектами).

## Как проверить руками

1. `npm run tauri dev` (или уже открытое окно).
2. Кнопка **«Запустить Git Bash»** — поднимает реальный ConPTY с `bash.exe` из Git for
   Windows. Это не полноценный Linux, но тот же GNU bash, поэтому `PS1`/`PROMPT_COMMAND`/
   `trap`/`history` ведут себя как на Linux-таргете — для проверки именно ConPTY- и
   bash-механики этого достаточно, без необходимости в реальном ssh на старте.
3. Кнопка **«Внедрить интеграцию»** — впечатывает одну строку (см.
   `src/shell-integration.ts`) с хуками OSC 133/633/7, прямо в открытую сессию.
4. Попробовать Tab-дополнение и стрелку вверх при наборе следующей команды — в панели
   «Блоки» должен появиться текст именно того, что бы реально выполнилось (источник —
   `history 1`, а не нажатия клавиш).
5. Кнопка **«Проверить историю»** — шлёт `history`; глазами убедиться, что строки
   внедрения в списке нет.
6. Кнопка **«Тест \r-перерисовки»** — гоняет locally искусственный прогресс-бар; в блоке
   должен остаться только финальный кадр, а не все промежуточные перерисовки.
7. Чек-лист слева кликабелен — отмечать вручную по мере проверки.

**Известное ограничение этого прогона:** Git Bash — не реальный Debian, поэтому `apt`/
`docker pull` живьём не проверить. Пункт «headless-рендер на `apt`/`docker pull`» из ТЗ
нужно будет отдельно прогнать через настоящий ssh-таргет (этап, где уже есть
`ssh.exe`-адаптер, см. `src/pty.ts` — спавнить можно любую программу, не только
`bash.exe`, так что переключение на `ssh.exe target` не требует изменений в Rust).

## Находки по ходу прототипа

- **Нельзя класть настоящий байт ESC в строку, которую "печатаешь" в шелл — только в ту,
  что шелл сам выводит.** Первая версия `shell-integration.ts` собирала инъекцию с реальным
  байтом `0x1b` внутри (строка на TS была буквально `"\x1b"`). Строка-инъекция — это ВВОД
  (мы её печатаем через `pty_write`), а не вывод, и эхо ввода — те же самые байты, что и
  любой другой вывод терминала. Поэтому встроенный ESC в самой печатаемой строке читался
  терминалом (и нашим же `registerOscHandler`) как настоящая управляющая последовательность
  и проглатывался — на реальном Debian это было видно буквально: куски вида `033]…` исчезали
  из эха на глазах, а `PS1` с ободранными `\[ \]` ломал подсчёт ширины промпта, из-за чего
  следующая набираемая строка (`apt update`) задваивалась посимвольно. Исправление — писать
  ESC как обычный печатаемый текст `\e` (документированный эскейп что для `PS1` в
  `decode_prompt_string`, что для `printf`): bash/printf превращают его в настоящий ESC-байт
  только КОГДА он им реально нужен — при показе промпта или вызове `printf`, то есть уже
  после того, как строка с ОПРЕДЕЛЕНИЕМ была напечатана и проэхуирована как обычный текст.
  См. `src/shell-integration.ts`.
- **`PROMPT_COMMAND` нельзя буквально "дописать в хвост".** Если дописать свой хук
  последним элементом (как дословно сказано в ТЗ), к моменту его исполнения `$?` уже
  затёрт либо существовавшим раньше `PROMPT_COMMAND`, либо даже собственным `local ec=$?`
  предыдущего хука — сам `local` как встроенная команда меняет `$?` на свой код возврата.
  Рабочий вариант: обернуть старый `PROMPT_COMMAND` в новую функцию, которая первым
  действием сохраняет `$?` в переменную и только потом вызывает старое содержимое через
  `eval`. Поведенчески это "сохранение", а не дословное добавление в конец строки/массива;
  для формы-массива bash 5.1 тот же принцип означает, что наш хук должен идти ПЕРВЫМ
  элементом, а не последним. См. комментарий в начале `src/shell-integration.ts`.
- **OSC 633 E лучше брать из `PS0` через `history 1`, а не через `trap DEBUG`.**
  `trap … DEBUG` стреляет на каждую простую команду, так что `a && b` дал бы два события
  вместо одного по логической команде пользователя. `PS0` печатается ровно один раз сразу
  после Enter и до начала выполнения, а `history 1` в этот момент уже содержит финальный
  текст (bash кладёт строку в историю до выполнения) — ровно то, что нужно для сверки
  "команда после Tab/истории" из чек-листа.
- **Git Bash (MSYS2) под голым ConPTY ломает Tab/историю/стрелки без `MSYS=enable_pcon`.**
  MSYS-рантайм не распознаёт ConPTY как нормальный терминал, пока не включён этот флаг
  (тот же трюк использует профиль Git Bash в Windows Terminal). Без него редактирование
  строки и навигация по истории визуально сыпались. Передаётся через `env` в `pty_spawn`
  (см. `src/pty.ts: spawnPty`, Rust принимает произвольный `HashMap<String,String>`).
  Для реального Linux-таргета через `ssh.exe` эта переменная не нужна — проблема
  специфична именно для Windows-бинарника `bash.exe` из MSYS2, не для ConPTY вообще.
- **Дедлок на ровном месте: поток `wait()` держал общий мьютекс всё время жизни сессии.**
  Первая версия бэкенда ждала код возврата процесса (`child.wait()`, блокируется часами)
  прямо под залоченным состоянием приложения — любое следующее обращение (запись
  нажатой клавиши, ресайз) намертво вставало в очередь на ту же блокировку. Исправлено:
  `Child` передаётся во владение потока ожидания напрямую, а в общей карте остаётся
  только лёгкий `clone_killer()` для принудительного завершения. Не риск из ТЗ, но
  ровно то, ради чего стадия "прототип" идёт до UI — такое не поймать на бумаге.

## Среда разработки

Установлено через winget с правами администратора 2026-10-20: Git, Node.js LTS,
Visual Studio Build Tools (workload VCTools, для MSVC-линковки Rust), rustup (toolchain
`stable-x86_64-pc-windows-msvc`, активен по умолчанию).

Скаффолд: `npm create tauri-app@latest` — шаблон `vanilla-ts`, менеджер `npm`,
identifier `com.pakochka.terminalmentor` (проект назывался `terminal-mentor`;
переименован в `termiinal`, см. `com.pakochka.termiinal` в текущем
`src-tauri/tauri.conf.json`).
